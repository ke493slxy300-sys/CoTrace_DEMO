# 队友 B · 数据库设计与实现工作日志

> “队友 B”是演示代号，应动态替换为当前项目中承担数据库职责的成员。

## 初始理解

任务看似是创建 users、items、orders 三张表，但核心问题其实是：两个买家同时下单时谁成功，以及订单插入失败后商品是否会错误地保持不可售。

## 我如何使用 AI 建议

- 接受：订单表保留商品外键，便于追踪来源。
- 否定并修正：AI 提议历史展示时关联当前商品；我要求订单同时保存标题、价格和币种快照。
- 否定并修正：AI 提议先查状态再更新；我改成带 `status='available'` 的条件更新。
- 接受但暂缓：新增 `reserved` 更准确，但会引出取消、拒绝和超时恢复。本节点只记录语义债务，不扩大迁移范围。

## 形成的实现判断

1. 条件 UPDATE 是并发竞争点，只有命中的请求能继续。
2. 商品更新与订单 INSERT 位于同一事务；约束失败会整体回滚。
3. MVP 对 `orders.item_id` 使用唯一索引，明确“一商品一订单”的当前规则。
4. 快照字段是交易事实，不因商品之后编辑而变化。

## 验证与风险

SQL 文件已按迁移顺序组织，并对外键、检查约束、索引和事务函数进行静态复核。尚未在真实 PostgreSQL 中执行并发与回滚集成测试。唯一索引也意味着取消后不能直接重新下单，后续需要改为部分唯一索引或明确历史订单策略。

## 建议进入长期记忆

- 用原子条件更新表达状态前置条件。
- 跨表业务不变量必须处于同一事务。
- 技术债要记录原因、影响和退出条件，而不只是写 TODO。
