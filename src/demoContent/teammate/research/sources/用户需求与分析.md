# 用户需求与分析：二手交易下单最小闭环

> 负责人显示为“队友 C”仅用于演示，不是最终队友姓名。产品应依据项目协作者与职责配置动态替换负责人信息。

> 证据边界：本文是为了 CoTrace Demo 构造的需求假设与实现对齐文档，不是经过真实用户访谈、问卷或线上数据验证的研究结论。所有“用户需要”均应在真实项目中继续验证。

## 1. 背景与目标

当前项目需要先打通从商品详情页发起购买，到后端创建订单，再向用户反馈结果的最小链路。此阶段的目标不是完成完整电商系统，而是验证前端、后端和数据库能否围绕同一组业务规则协作。

成功标准：买家能明确知道操作是否成功、当前处于什么状态；卖家不会面对同一件商品的多个有效订单；团队能从代码和说明中看出暂未覆盖的边界。

## 2. 目标用户与核心目标

| 角色 | 此阶段目标 | 最担心的问题 |
|---|---|---|
| 买家 | 在商品详情页快速发起购买，并获得明确反馈 | 重复点击、失败原因不明、价格在下单后变化 |
| 卖家 | 接收唯一且可处理的订单 | 同一商品被多人同时买下、状态含义不清 |
| 项目成员 | 用稳定接口与约束完成联调 | 前后端各自理解正确，但组合后语义冲突 |

## 3. 关键场景

### 场景 A：正常创建订单

买家在可售商品详情页点击“立即购买”。页面进入处理中状态，后端创建订单并返回订单快照，页面展示“订单已创建，等待卖家确认”。

### 场景 B：重复操作

买家连续点击按钮。前端应禁用按钮并复用当前请求；后端仍必须通过数据库条件更新保证只创建一个订单。前端限制是体验优化，不是并发安全边界。

### 场景 C：商品已不可售

另一位买家先完成创建订单。当前请求收到稳定错误码 `ITEM_NOT_AVAILABLE`，页面提示“商品状态已变化，请刷新后重试”，不能只显示未知异常。

### 场景 D：历史信息发生变化

卖家之后修改商品标题或价格。已创建订单仍展示下单时的标题、价格和币种快照。

## 4. 用户旅程

| 阶段 | 用户动作 | 系统反馈 | 体验要求 |
|---|---|---|---|
| 判断 | 查看标题、价格与卖家信息 | 展示当前商品详情 | 信息足以确认购买对象 |
| 发起 | 点击“立即购买” | 按钮进入处理中且不可重复点击 | 状态变化立即可见 |
| 等待 | 等待接口返回 | 保留当前页面上下文 | 不制造第二个请求 |
| 成功 | 查看订单结果 | 展示快照和“等待卖家确认” | 明确交易已建立但尚未完成 |
| 失败 | 查看原因并决定下一步 | 业务错误可读，必要时允许重试 | 不把所有错误归为网络失败 |

## 5. 需求优先级

### P0：本次联调必须满足

- 从商品详情页调用 `POST /api/orders`。
- 客户端请求体只提交商品 ID；后端从已认证会话取得买家 ID，并拒绝买家购买自己的商品。
- 请求进行中禁止重复提交，但后端仍独立保证幂等边界和并发一致性。
- 订单写入商品标题、价格、币种快照。
- 更新商品状态与写入订单处于同一数据库事务。
- 返回稳定业务错误码，前端映射为用户可理解的文案。
- 成功后明确显示订单处于“等待卖家确认”。

### P1：应在后续迭代补全

- 显式 `reserved` 商品状态，替代当前用 `sold` 表示临时锁定的折中。
- 卖家确认、拒绝和超时释放商品。
- 订单取消后的商品恢复规则。
- 更完整的幂等键与请求追踪。

### 本阶段不做

- 支付、退款、物流与售后。
- 聊天、议价和优惠券。
- 风控、信用评价与复杂库存。

## 6. 统一业务规则

1. 一个商品在 MVP 中最多形成一个订单。
2. 只有 `available` 状态商品可创建订单。
3. 买家不能购买自己的商品。
4. 订单历史使用下单时快照，不使用商品当前值覆盖。
5. 当前数据库把商品更新为 `sold`，但订单状态是 `pending_seller_confirmation`。这是公开记录的限制，不应被 UI 文案掩盖。
6. 任一步失败，商品状态和订单数据必须一起回滚。

## 7. 跨节点对齐

| 规则 | 前端节点 | 后端节点 | 数据库节点 |
|---|---|---|---|
| 防重复 | 请求中禁用按钮 | 校验并映射冲突 | 条件更新与唯一约束 |
| 错误反馈 | 错误码转用户文案 | 返回稳定错误码 | 用受影响行数识别竞争失败 |
| 历史一致 | 展示响应快照 | 响应返回快照字段 | 订单保存快照列 |
| 状态语义 | 显示等待卖家确认 | 返回 pending 状态 | 暂用 sold 锁定并记录限制 |

## 8. 验收标准

- Given 商品可售且买卖双方不同，When 买家发起购买，Then 只创建一个订单，返回快照并显示等待确认。
- Given 请求仍在处理中，When 买家再次点击，Then 前端不发送第二个请求。
- Given 两个买家同时购买，When 数据库竞争发生，Then 最多一个请求成功，失败方得到可识别的不可售结果。
- Given 订单写入失败，When 事务回滚，Then 商品仍保持原可售状态。
- Given 商品信息之后变化，When 打开历史订单，Then 仍显示下单时快照。
- Given 后端返回稳定业务错误码，When 前端处理失败，Then 显示对应可操作提示。

## 9. 待验证假设与风险

- 用户是否把“订单已创建”误解为卖家已经成交确认。
- `sold` 与“等待卖家确认”的组合是否造成团队或用户的状态误判。
- MVP 的“一商品一订单”是否允许取消后重新上架；当前唯一约束尚不支持该路径。
- 网络超时后，用户重试是否可能在看不到首个响应的情况下制造歧义。
- 真实用户更希望失败后自动刷新商品状态，还是保留页面并手动刷新。

## 10. 项目理解 Agent 摘要

本节点把用户目标转化为跨前端、后端与数据库可验证的约束。当前最关键的判断不是补齐更多功能，而是把“已创建订单”“等待卖家确认”“商品已锁定”三种语义明确分开，并公开记录 MVP 的状态折中。
