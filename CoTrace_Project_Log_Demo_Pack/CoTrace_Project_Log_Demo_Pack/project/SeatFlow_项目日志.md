## 决策历史

### 04月18日 · 预约状态：创建成功不等于预约已确认

- 问题：前端在创建预约后直接显示“预约成功”，数据库实际上只完成座位锁定。
- 讨论：团队比较了单一 `booked` 与 `reserved / confirmed` 两阶段状态。
- 决策：创建预约只进入 `reserved`，后续确认才进入 `confirmed`。
- 理由：数据库、API 与界面必须表达同一个流程阶段。
- 状态：任务已完成；成果已提交；团队决定已确认。

### 04月26日 · 重复预约：数据库决定唯一成功请求

- 问题：连续点击和并发请求可能产生重复预约。
- 讨论：前端禁用按钮只能解决单页面重复操作。
- 决策：前端保留提交中状态，数据库使用条件更新和唯一约束。
- 理由：体验保护不能替代数据一致性。
- 状态：任务已完成；成果已提交；团队决定已确认。

### 05月08日 · 范围控制：暂缓自动释放与通知系统

- 问题：预约超时需要释放座位，AI 建议同时加入定时任务、通知和签到。
- 讨论：完整方案合理，但超出课程 Demo 的可验证范围。
- 决策：记录超时释放风险，本阶段只完成状态边界和手动取消。
- 理由：优先保证预约主链路可解释、可测试。
- 状态：任务已完成；成果已提交；团队决定已确认。
