## 1. users

| 字段 | 类型 | 说明 |
|---|---|---|
| id | varchar | 用户唯一标识 |
| name | varchar | 用户显示名称 |
| created_at | timestamp | 创建时间 |

## 2. items

| 字段 | 类型 | 说明 |
|---|---|---|
| id | varchar | 商品唯一标识 |
| seller_id | varchar | 发布者，对应 users.id |
| title | varchar | 商品标题 |
| price | decimal(10,2) | 当前标价 |
| status | varchar | `available` 或 `sold` |
| created_at | timestamp | 发布时间 |
| updated_at | timestamp | 最近修改时间 |

建议索引：

- `items(seller_id)`；
- `items(status, created_at)`。

## 3. orders

## 4. 为什么保存订单快照

商品标题和价格属于可变信息。订单属于历史事实，必须保留交易发生时的数据。若订单详情始终读取商品表，卖家修改标题或价格后，历史订单会显示错误信息。

本阶段仅复制：

- 商品标题；
- 商品价格。

不复制图片、描述和卖家个人资料，以免形成不必要的数据重复。

## 5. 条件更新建议

真实数据库中，商品占用应表达为带条件的更新：

    UPDATE items
    SET status = 'sold', updated_at = CURRENT_TIMESTAMP
    WHERE id = :itemId AND status = 'available';

应用层必须检查受影响行数：

- 1 行：占用成功，可以继续创建订单；
- 0 行：商品不存在或已经不可售，需要终止创建。

## 6. 事务边界

建议将以下操作放入同一事务：

1. 条件更新商品状态；
2. 写入订单及快照；
3. 提交事务。

订单写入失败时应撤销商品更新。当前 Demo 的内存仓储只能用补偿恢复模拟，不能替代真实事务。

## 7. 后续结构

如增加 `reserved` 状态，需要同时定义：

- 预留开始时间；
- 预留过期时间；
- 卖家拒绝后的恢复；
- 取消订单的责任方；
- 同一商品的唯一有效订单约束。
